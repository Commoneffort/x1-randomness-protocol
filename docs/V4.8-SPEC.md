## Problem

`consecutive_misses` is documented as "reset to 0 on successful reveal". It is
not. The only resets in the deployed program are `register_validator` and
`refresh_validator_status`. `reveal_via_ee` never touches the field, so misses
are **cumulative for the entire life of a registration** — a validator that
misses one round, reveals correctly for six months, then misses another, is two
misses closer to the deactivation threshold of five with nothing having gone
wrong in between.

V4.7.1 removed the remote-DoS half of this (`mark_validator_missed` can no
longer be aimed at rounds a validator revealed in or was excluded from), and
`run-round.js` carries a keeper-side guard that calls `refresh_validator_status`
on any validator showing a non-zero counter. Neither is the fix. The guard only
holds while a crank is running, and it is repairing state that should never have
accumulated. The counter should mean "misses **in a row**, right now", and only
the reveal path can honestly reset it.

## Change

### Program — `programs/randomness-wrapper/src/lib.rs`

**1. `RevealViaEe`: `validator_reg` gains `mut`.**

```rust
    #[account(
        mut,                                    // ← added
        seeds = [b"val-reg", validator_reg.identity.as_ref()],
        bump = validator_reg.bump,
        constraint = validator_reg.active @ RandomnessError::ValidatorInactive,
        constraint = validator_reg.x1_randomness_authority == contributor.key() @ RandomnessError::Unauthorized,
    )]
    pub validator_reg: Account<'info, ValidatorRegistration>,
```

**2. `reveal_via_ee` handler: record the participation.** After the existing
`vr.contributor = ctx.accounts.validator_reg.x1_randomness_authority;` and
before `Ok(())`:

```rust
        let reg = &mut ctx.accounts.validator_reg;
        reg.consecutive_misses      = 0;
        reg.last_round_participated = ctx.accounts.protocol_config.ee_v4_round_id;
        reg.last_active_slot        = Clock::get()?.slot;
```

No account layout change — all three fields already exist in the 171-byte
`ValidatorRegistration`. **No migration, no realloc.**

`last_active_slot` is currently written on commit only. Writing it on reveal too
makes the dashboard's liveness signal reflect completed work rather than
attempted work, which is what operators expect it to mean.

### Daemon — `keeper/validator-daemon.js`

One line in `ixReveal`, key index 5:

```diff
-      { pubkey: reg,                     isSigner: false, isWritable: false },
+      { pubkey: reg,                     isSigner: false, isWritable: true  },
```

### Keeper — `keeper/run-round.js`

`resetAccumulatedMisses()` stays. It becomes a belt-and-braces backstop for
counters accrued before V4.8 and for any validator whose reveals are failing for
an unrelated reason. Its adaptive throttle already makes it nearly free while
every counter reads zero. Do not remove it in the same release as the program
change — remove it, if ever, only after V4.8 has run clean for a while.

## Rollout order — daemons first, then deploy

**This order is mandatory and is the whole reason V4.8 needs scheduling.**

1. Announce the commit hash and the deploy window.
2. **Every operator pulls and restarts** (see `VALIDATORS.md` → "Kind B").
3. Collect confirmations from all active validators.
4. **Only then deploy.**

### Why this direction is the safe one

Verified against `anchor-lang` 0.30.1: `Account::try_accounts` checks the owner
and the discriminator and **performs no `is_writable` check**. The writability
check is generated solely by the `mut` constraint (`ConstraintMut`), and the
other `is_writable` references in `account.rs` are in `AccountsExit` and in a
`DerefMut` guard behind the `anchor-debug` feature.

The consequence:

| | old program | new program |
|---|---|---|
| **old daemon** (`isWritable: false`) | works | **every reveal fails** `ConstraintMut` |
| **new daemon** (`isWritable: true`) | works — extra writability is ignored | works |

A new daemon is compatible with both programs; an old daemon is compatible with
only one. So daemons can move early at no cost, and the deploy is then a
zero-downtime cutover. Deploying first would break reveals for the entire set
until the last operator caught up — and because `m = 5` of `n = 7`, that means
rounds stop finalizing, not merely that stragglers miss out.

### If an operator misses the window

They fail reveals until they pull and restart, losing their 0.01 XNT bond on any
round they commit to in the meantime. Finalization survives up to two such
validators (`m = 5`, `n = 7`). Three or more stale daemons stall rounds — which
is why step 3 collects confirmations rather than assuming them.

Nothing about this is irreversible: the program can be rolled back to the V4.7.1
`.so`, and new daemons keep working against it.

## Out of scope

Deliberately **not** in V4.8:

- **`claim_validator_reward` closing the `ValidatorReveal` PDA.** The second
  half of the original DoS write-up. V4.7.1 made the closure harmless by proving
  misses from the EE round's contributor table instead, so this is now a
  cosmetic wart rather than a vulnerability. Keeping the close returns
  ~0.00146 XNT of rent per round to validators; removing it would cost them that
  and buy nothing.
- **Any change to `EE_V4_N_CONTRIBUTORS` (7) or `EE_V4_M_THRESHOLD` (5).**
  Unchanged, by explicit instruction.
- **The `CloseEscrow` lockup** (`require!(!fee_distributed)` makes distributed
  escrows permanently unclosable — 5.27 XNT stranded across 298 accounts).
  A separate fix; it needs no validator coordination and should not be bundled
  with one that does.
